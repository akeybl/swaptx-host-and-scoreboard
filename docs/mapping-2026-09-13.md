# SWAPTX Evolver radio mapping — live session, 2026-09-13

Sniffer: Lonely Binary ESP32-WROOM-32UE, firmware `swaptx-sniffer 1.1` (promiscuous, all frames,
channel survey, BLE scan). Raw log: `captures/20260913-200253.jsonl` (one `<unix ts>\t<json>` per line).
Gear: one Evolver gun (unique ID 2) + its wireless headset; second gun/headset later.

## Confirmed so far

1. **Channel 1.** Adjacent-channel bleed makes the gear audible on 2 and 3 too, but RSSI is best on 1.
   (The dongle's silence-triggered autoscan locked onto channel 3 by bleed; autoscan is now off.)
2. **A headset alone is silent** on ESP-NOW (all 13 channels), on plain Wi-Fi, and on BLE. Only Apple
   devices rotating their BLE addresses showed up as "new".
3. **The headset is the ESP-NOW radio; the gun is a passenger.** Powering the gun off/on with the
   headset up produced nothing; powering the headset off/on with the gun up restarted the beacon.
   Sender address is spoofed to the gun's ID (`00:00:00:00:00:02` for gun 2), destination is the host
   address `00:00:00:00:00:ff`. The gun "screams" when the headset link drops.
4. **The gun–headset link is invisible to the ESP32**: no new Wi-Fi or BLE sender at close range when
   they pair. Proprietary 2.4 GHz or IR.
5. **Report-in beacon `36,79`.** Sent by the headset for ~3 minutes after it links to a gun: once
   every 4.3 s, sequence numbers 0..40 (41 messages), then it stops until the next headset link.
   Each message is a unicast to the host and, with no host ACK, the radio retries it 10–28 times
   (same 802.11 sequence number) — fold retries by (src, seq, payload).
   Payload is a 32-byte text field followed by uninitialised heap (ESP-IDF canaries 0xBAAD5678,
   RAM pointers 0x3FFFxxxx); total length 72 or 80 bytes. Only the text matters.

   ```
   36,79,<player0>,<state>,<team>,3,1,42
   ```
   - `player0`: 0-based gun ID (1 = gun 2).
   - `state`: `100` for the first ~4 beacons after a fresh headset link (no gun data yet, headset
     shows yellow), then `1` once the headset has the gun's settings.
   - `team`: **0 red, 1 blue, 2 free-for-all (yellow), 3 green** — matches `TEAM_NAMES` in
     `swaptx/protocol.py`. The gun's own cycle order is red → green → free-for-all → blue.
     Changing team updates the beacon within one period (4.3 s).
   - The last two tokens (`3,1`) did not change with team, game mode (Team Battle / Battle Royale),
     health (low/high) or storm (on/off). Unknown, possibly firmware/protocol version.
   The DIY LaserTagMods host reads only the first token of this message ("player N reported in"),
   which is why its author never saw the team here.

6. **Shots, empty-clip clicks and reloads put nothing on the air.** Only hits reach the radio.
7. **Admin mode by itself is silent.** No frame appeared when the headset entered admin mode and the
   admin picked Team Battle; nothing periodic from the host either.
8. **Start beacon `36,65`** appears only when the admin starts a game: sent twice (seq 0 and 1, ~0.1 s
   apart) from the host address `00:00:00:00:00:ff` to broadcast (no retries on a broadcast). Seen:
   ```
   36,65,1,1,0,1,0,0,1,1,42
   ```

   token is which still needs confirming by changing one admin setting at a time.

## Summary for the board

the host side of this table; storm-time behaviour and the timer-expiry message were never observed.

mapping the same evening; replaying this capture reconstructs every game played.
